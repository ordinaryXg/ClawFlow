# ClawFlow 开发流程骨架（AI 协作版）

> 目的：把“需求/计划/实现/验证/交付/留痕”统一成可重复流程，减少上下文丢失，让 AI 能稳定接棒。

## 0. 输入规范（启动一个工作项）

每次开始一个功能/改动，至少提供：

- **工作项名称**：一句话（可作为分支名/PR 标题）
- **目标（Goal）**：要达成什么用户价值
- **非目标（Non-goal）**：明确不做什么（防止范围膨胀）
- **涉及模块**：Main / Preload / Renderer / OpenClaw / Build
- **验收标准（AC）**：可操作、可验证（建议 3-7 条）
- **风险与约束**：安全边界、兼容性、性能、依赖外部环境等

## 1. 设计阶段（写清“怎么做”之前先写“为什么这样做”）

产物建议写在任务文档或日志中（简短即可）：

- **方案 A/B 对比**：为什么选这个（关键权衡点）
- **接口约定**：
  - IPC channel 命名与 payload 结构
  - 错误码/错误消息约定（给 UI 的提示策略）
- **数据模型**：关键 type/interface（只写核心字段）
- **回滚/降级**：失败时用户会看到什么、能否继续使用

## 2. 实现阶段（最小可用 → 完整）

推荐顺序：

- **先打通链路**：Renderer → Preload → Main → OpenClaw（或 Mock）跑通
- **再补体验**：loading/错误/空状态/禁用态/重试
- **最后做“正确性”**：边界条件、状态一致性、并发/取消、资源回收

## 3. 验证阶段（不要“看起来能用”，要可复现）

- **手动验收清单**：按 AC 逐条勾选，写下验证方法（点击路径/命令/预期）
- **最小自动化**（可选但推荐）：
  - Lint / Typecheck
  - 关键逻辑单测（尤其是引擎封装、store、解析/脱敏）

## 4. 交付阶段（让后续维护的人更轻松）

- **变更点摘要**：3-7 条（做了什么 + 为什么）
- **涉及文件列表**：便于回溯
- **已知问题/后续工作**：明确下一步

## 5. 留痕与知识沉淀（AI 可读性关键）

- **短记录**写在任务下方（最多 5-10 行）
- **长记录**写进 `90_LOGS/`（按天/主题）
- **架构变化**同步更新 `02_ARCHITECTURE.md`
- **计划变化**同步更新 `04_ROADMAP.md` 与 `06_TASKS.md`
